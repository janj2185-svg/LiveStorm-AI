# Screen authoring guide

How to build a SYLORA screen so it matches every other one. Read this before
writing any screen code.

---

## 1. Where things live

```
src/design-system/
  tokens/       colour, type, space, motion, elevation  (TypeScript, authoritative)
  styles/       tokens.css (GENERATED), base, brand, components, patterns, screens
  brand/        Logo.tsx — LogoMark, LogoWordmark, LogoLockup, AiOrb
  icons/        Icon.tsx — <Icon name="..." size={20} />
  primitives/   index.tsx — every reusable control
  patterns/     AppShell.tsx — shell, PageHeader

src/screens/
  data.ts       shared demo content — ALWAYS use this, never invent lorem ipsum
  components.tsx  PostCard, StreamCard, CreatorCard, Media, BarChart, Sparkline,
                  Donut, ListRow, ScreenSection
  types.ts      ScreenDefinition
  <group>/
    index.ts        exports <GROUP>_SCREENS: ScreenDefinition[]
    <group>.css     all CSS for this group's screens
    XScreen.tsx     one file per screen
```

**Never edit** `src/design-system/styles/tokens.css` — it is generated by
`pnpm tokens` from the TypeScript token modules.

**Never edit** files outside your assigned group. `registry.ts` already imports
every group; you only fill in your own `index.ts`.

---

## 2. Hard rules

1. **No literal values.** No hex colours, no `px` font sizes, no raw
   durations. Every value comes from a `--sy-*` custom property. If a value you
   need does not exist, use the nearest token rather than inventing one.
2. **No placeholders.** No "Lorem ipsum", no "Title here", no empty `<div>`
   standing in for content. Pull from `src/screens/data.ts`. If you need data
   that is not there, write realistic content inline — real names, real
   sentences, believable numbers, including some that are awkwardly long.
3. **No images.** There are no photographic assets. Use `<Media seed="..." />`,
   which synthesises deterministic cover art. Never render a grey box.
4. **Container queries, not media queries.** Screens sit inside `.sy-screen`,
   which declares `container: screen / inline-size`. Write
   `@container screen (min-width: 768px)`. A `@media` query in a screen
   stylesheet is a bug — it would respond to the browser window instead of the
   device frame.
5. **Accessibility is not optional.** Every icon-only control gets an
   `aria-label`. Every input gets a label. State is never carried by colour
   alone — pair it with an icon, a weight change, or text. Headings descend in
   order.
6. **Comment the design decision, not the code.** Explain *why* a layout,
   ordering or interaction was chosen. Never write comments like
   "// map over posts".

## 3. Screen skeleton

```tsx
/**
 * <Screen name>
 * -------------------------------------------------------------------------
 * <2-6 lines: what decision this screen optimises for, what the information
 * hierarchy is, and any non-obvious trade-off you made.>
 */

import { Button, Surface /* ... */ } from '../../design-system/primitives';
import { ScreenSection } from '../components';
import { SOMETHING } from '../data';

export function ExampleScreen() {
  return (
    <div className="sy-screen">
      <div className="sy-screen__inner">
        <ScreenSection title="Section">…</ScreenSection>
      </div>
    </div>
  );
}
```

Register it in your group's `index.ts`:

```ts
import type { ScreenDefinition } from '../types';
import { ExampleScreen } from './ExampleScreen';

export const EXAMPLE_SCREENS: ScreenDefinition[] = [
  {
    id: 'example',
    name: 'Example',
    group: 'Core',
    navId: 'home',              // which shell destination highlights
    purpose: 'One sentence on what this screen is for.',
    component: ExampleScreen,
    // contextPanel: ExampleContextPanel,   optional, expanded posture only
    // contextPanelTitle: 'Details',
    // immersive: true,                     full-bleed, no shell chrome
    // preferredDevice: 'iphone',
  },
];
```

## 7. Responsive expectations

**Screens respond to their content column, not to the device.** The shell takes
its chrome out first, and how much it takes depends on whether the screen
supplies a `contextPanel`:

| Device | Frame | Column, no context panel | Column, with context panel |
|---|---|---|---|
| iPhone | 393 | 393 | 393 |
| Android | 412 | 412 | 412 |
| Tablet | 834 | 758 | 758 |
| Web | 1280 | 1016 | **676** |
| Desktop | 1512 | 1248 | 908 |

The rail costs 76px collapsed and 264px expanded; the context panel costs
340px and only appears in the expanded posture.

Two traps this creates:

- With a context panel, **web at 1280 is narrower than tablet at 834**. 676px
  is the tightest multi-column case in the product.
- **Device-shaped numbers do not work.** `min-width: 768px` never fires on the
  tablet's 758px column. `min-width: 1024px` never fires at web when a context
  panel is present.

Use these thresholds instead, which sit either side of the real widths rather
than on top of them:

| Threshold | Fires at | Use for |
|---|---|---|
| `560` | 758, 1016, 1248 (and 676/908 with panel) | Two columns, denser padding, retiring in-screen search |
| `840` | 1016, 1248, 908 | Three columns, wider gaps |
| `880` | 1016, 1248, 908 | Sidebar layouts |

Every screen must hold at **393**, **758**, **676** and **1248**. Nothing may
be pinned to a fixed width, tap targets stay at or above 44px, and the bottom
84px of the compact posture is reserved for the floating tab bar.
